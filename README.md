# RoboMaster EP — Grid SLAM และ DFS Exploration

ระบบสำรวจเขาวงกตแบบช่อง 60 × 60 ซม. หุ่นเริ่มโดยไม่รู้แผนที่ ใช้ ToF บน Gimbal
สแกนกำแพงแล้วสร้างแผนที่ระหว่างรัน ใช้ DFS เลือกช่องที่ยังไม่เคยไปและย้อนกลับ
เมื่อไม่มีทางใหม่ สำรวจเสร็จเมื่อกลับจุดเริ่มและไม่มีช่องที่เข้าถึงได้เหลือให้สำรวจ

**Sharp ซ้าย–ขวาใช้ PID Centering ส่วน ToF ใช้ทั้งสร้างแผนที่และตรวจการชนด้านหน้า**
Position/odometry และ yaw ใช้คาดตำแหน่ง โดยระยะถึงกำแพงที่เคยบันทึกไว้ช่วยแก้
ตำแหน่งและลดความไม่แน่นอนเมื่อย้อนผ่านทางเดิม

## หลักการทำงาน

1. เริ่มจากกลางช่องที่กำหนดใน `map.start` (ค่าเริ่มต้น `(0, 0)`) หันไปตามแกนทางเดิน ให้ทิศเริ่มต้นเป็น N
2. หยุด chassis และปรับ yaw ให้ตรงแกน Grid
3. หมุน Gimbal วัดหน้า ขวา หลัง และซ้าย รอ action จบและพักตามเวลา settle
   แล้วเก็บ ToF ใหม่หลาย packet ใช้ median ของระยะที่ calibrate แล้ว
4. เทียบ scan กับกำแพงเดิมเพื่อแก้ตำแหน่ง จากนั้นบันทึกกำแพง/ทางเปิดของช่องปัจจุบัน
   กำแพงร่วมของสองช่องเก็บเป็น edge เดียว ช่องที่ไม่รู้ข้อมูลยังเป็น unknown
5. DFS เลือกทางเปิดไปช่องที่ยังไม่สำรวจ ถ้าไม่มีให้ย้อนตาม stack
6. เลี้ยว chassis หัน ToF กลับหน้าหุ่นและรอข้อมูลระยะใหม่ก่อนเดิน
7. เดินหนึ่งช่องด้วย Sharp Centering และ PID รักษา yaw อ่าน ToF ด้านหน้าต่อเนื่อง
   ใช้ระยะที่น้อยกว่าระหว่าง raw ที่ calibrate แล้วกับ filtered เพื่อไม่ให้ตัวกรองหน่วงการหยุด
8. ยืนยันระยะเดินก่อนเปลี่ยนหมายเลขช่อง แล้วสแกนซ้ำ ความคลาด odometry บันทึกเตือน

ข้อมูลเก่า ToF ไม่หันหน้า action ล้มเหลว เดินไม่ถึงช่อง scan ขัดกับแผนที่
หรือความไม่แน่นอนตำแหน่งสูงเกินกำหนด จะหยุดและบันทึกแผนที่บางส่วน
หากถึงจำนวนช่อง/จำนวนก้าวสูงสุดจะรายงาน `limit_reached` ไม่ใช่ `completed`

## ขอบเขต SLAM

เป็น **SLAM แบบจำกัดด้วย Grid**: คาดตำแหน่งต่อเนื่องด้วย odometry แล้วใช้ระยะ
ถึงกำแพงที่รู้จักอัปเดตตำแหน่ง x/y พร้อม covariance แยกแกน ใช้ IMU yaw เป็นทิศทาง
และกลับมาใช้ landmark เดิมเมื่อผ่านช่องเดิม การจับคู่ใช้ ray ตามสี่ทิศผ่าน edge ที่รู้แล้ว
ไม่มีการถือว่าช่องใหม่ถูกต้องเพียงเพราะส่งคำสั่งเดินครบ

ระบบสมมติว่ากำแพงตรงตามแนว Grid และสนามคงที่ ไม่ได้ทำ pose graph optimization,
scan matching แบบอิสระทุกมุม หรือแก้ประวัติแผนที่ทั้งชุดย้อนหลัง ถ้า odometry ผิด
จนระบุช่องไม่ได้จะหยุด ไม่พยายาม relocalize ในเขาวงกตที่กำแพงเหมือนกันหลายจุด
ทางเดินยาวที่ไม่เห็น landmark ตามแนวเดินอาจมีความไม่แน่นอนสะสมจนต้องหยุด

## เมนูเลือกงาน


การวิเคราะห์ Log เลือกรอบรันจากรายการ ส่วนประเมินแผนที่ใช้ `slam.output`
และ `paths.ground_truth` ที่ตั้งใน YAML คำสั่ง CLI ด้านล่างยังใช้ได้เหมือนเดิม

## สำรวจและสร้างแผนที่

```bash
# สำรวจสนามจำลองที่สร้างระหว่างรัน ไม่มีไฟล์แผนที่หรือเส้นทางเป็น input
.venv/bin/python main.py explore --mock --output /tmp/explored_map.json

# เชื่อมต่อ Wi-Fi AP ของหุ่น แล้วสำรวจสนามจริง
.venv/bin/python main.py explore --conn-type ap

# ระบุตำแหน่งผลลัพธ์เอง
.venv/bin/python main.py explore --conn-type ap --output data/my_exploration.json
```

ค่าเริ่มต้นบันทึก `data/explored_map.json` ทุกครั้งที่สแกนสำเร็จ และตอนสิ้นสุด/ล้มเหลว
ไฟล์นี้เป็น **ผลลัพธ์การสำรวจ** โปรแกรมไม่โหลดกลับมาเป็นแผนที่เริ่มต้น
รันซ้ำที่ output เดิมจะแทนที่ไฟล์เดิม ถ้าต้องการเก็บหลายรอบให้เปลี่ยน `--output`
กด Ctrl+C เพื่อหยุดและบันทึกแผนที่บางส่วน โหมดจริงไม่ fallback ไปสนามจำลอง

ผลลัพธ์ JSON มี `status`, `error`, `visited`, `edges`, `pose`, `variance_m2`,
`trajectory`, `scans`, `events`, `start_cell`, `start_pose` และ `landmark_matches` ทิศ N/E/S/W อ้างอิงกับทิศเริ่มต้น
ไม่ใช่ทิศเข็มทิศจริง: `+x` ไปข้างหน้าเริ่มต้น, `+y` ไปทางขวา, yaw บวกตามเข็มนาฬิกา
ค่าของ `edges.wall` เป็น true/false; edge ที่ไม่อยู่ในไฟล์หมายถึงยังไม่รู้

โหมด `explore --mock` จำลองระยะและ odometry ที่มี bias เพื่อทดสอบ DFS และ localization
สนามจำลองอยู่ใน backend เท่านั้น ตัวสำรวจอ่านได้เฉพาะ scan และผลการเดิน
โหมดนี้ไม่ได้จำลองพลศาสตร์มอเตอร์หรือทดสอบ PID บนฮาร์ดแวร์

## หยุดและกลับเมนู Calibration

ระหว่างกรอกระยะจริงของเซนเซอร์ พิมพ์ `q` แล้ว Enter เพื่อหยุดเก็บค่า
ตัวอย่างที่บันทึกแล้วคงอยู่ และกลับไปเมนู Calibration โดยไม่ตัดการเชื่อมต่อหุ่น
เลือก Sharp ซ้าย/ขวาหรือ ToF เพื่อเก็บต่อได้โดยใช้ connection เดิม
เมื่อเก็บครบจำนวนตัวอย่างหรือคำนวณสมการเสร็จ จะกลับเมนูนี้เช่นกัน
เลือก 0 เพื่อจบเมนู Calibration และปิด connection; EOF/Ctrl+C จบ session เช่นกัน
การหยุด ToF จะยกเลิกเฉพาะ subscription ของการเก็บตัวอย่าง ไม่ปิด connection
คำสั่ง `main.py calibrate collect-live ...` ใช้ session เดียวกันและกลับเมนูได้ด้วย
ส่วน `calibrate.py` แบบ standalone จบโปรแกรมเมื่อหยุดเก็บข้อมูล

## ผลลัพธ์สำหรับส่ง Classwork 8

เมื่อจบ `explore` จะสร้างไฟล์เพิ่มข้าง JSON:

- `<ชื่อไฟล์>_map.png`: ภาพแผนที่ที่สำรวจแล้วและเส้นทางตำแหน่งที่ประเมิน
- `<ชื่อไฟล์>_events.csv`: Log การสแกน การเดิน/ย้อนกลับ และสถานะจบ
- โหมดหุ่นจริงยังบันทึก sensor telemetry ลง `telemetry_logs/run*/`

JSON รายงานจุดเริ่มตาม `map.start`, ขนาดแผนที่ใน `map_info` และจุดจบที่ประเมิน
ถ้ารันล้มเหลว จุดในภาพคือ SLAM pose ล่าสุดที่ยืนยันได้ อาจไม่ใช่ตำแหน่งจริง
หลังการเคลื่อนที่ที่ล้มเหลว ให้ดู `status`, `error` และ telemetry ประกอบ

เทียบ Ground Truth **หลังภารกิจ** ด้วย:

```bash
.venv/bin/python main.py evaluate-map data/explored_map.json data/ground_truth.json
```

รูปแบบ Ground Truth (ต้องใช้พิกัด/ทิศเดียวกับผลสำรวจ):

```json
{"cells": [{"cell": [0, 0], "walls": {"N": false, "E": true, "S": true, "W": true}}]}
```

`Coverage` = จำนวนช่องสำรวจที่อยู่ใน Ground Truth / ช่องทั้งหมด × 100
`Map Accuracy` = จำนวนช่องที่กำแพงทั้งสี่ทิศตรง Ground Truth / ช่องทั้งหมด × 100
ช่องไม่สำรวจหรือกำแพงไม่ครบถือว่ายังทายไม่ถูก รายงานช่องที่อยู่นอก Ground Truth แยกด้วย
บันทึกผลเป็น `<ชื่อไฟล์>_metrics.json` โดยไม่ส่ง Ground Truth ให้ระบบสำรวจ

## การตั้งค่าและการนำไปใช้กับหุ่นจริง

แก้ `config/settings.yaml` แล้วเริ่มโปรแกรมใหม่ relative paths ภายในไฟล์อ้างอิง
จากรากโปรเจกต์ CLI เช่น `--conn-type`, `--calibration`, `--output` ใช้แทนค่าเริ่มต้น

- `robot`: โหมดเชื่อมต่อและ `yaw_command_sign` สำหรับแปลง yaw ไปเป็นคำสั่ง SDK
- `sensors`: พอร์ต Sharp ช่อง ToF ความถี่ และตัวกรอง
- `navigation`, `pid`: ขนาดช่อง ความเร็วระหว่างเดิน PID ระยะหยุด และระยะกำแพง
- `gimbal`: มุม pitch ความเร็ว เวลารอ และตำแหน่งติดตั้ง ToF
- `map`: จำนวนแถว–คอลัมน์และพิกัดช่องเริ่มต้น ใช้ทั้งสนามจริงและสนามจำลอง
- `slam`: ความหนากำแพง เกณฑ์ matching/ความไม่แน่นอน จำนวน sample ขีดจำกัดสำรวจ และ output
- `paths`, `calibration`, `telemetry`, `system`, `simulation`: ไฟล์ สมการ บัฟเฟอร์ และค่าการทดสอบ

ตั้งขนาดแผนที่และจุดเริ่มต้นได้ดังนี้:

```yaml
map:
  rows: 3
  columns: 3
  start:
    x: 0
    y: 0
```

พิกัดเริ่มต้นเป็นหมายเลขช่อง เริ่มนับจาก 0: `x` คือแถวตามแกนหน้าเริ่มต้น
(`0 <= x < rows`), `y` คือคอลัมน์ตามแกนขวา (`0 <= y < columns`)
ศูนย์กลางช่อง `(x,y)` มีตำแหน่งในแผนที่เป็น `(x × grid_size_m, y × grid_size_m)` เมตร
odometry ของหุ่นยังเริ่มที่ `(0,0)` แต่ SLAM บวกตำแหน่งเริ่มในแผนที่ให้
ขนาดนี้ไม่ระบุกำแพงล่วงหน้า ทุกกำแพงต้องวัดจริง หากพบทางเปิดออกนอกขอบเขต
จะหยุดและแจ้งให้ตรวจขนาด/จุดเริ่ม แทนการเดินออกนอกพื้นที่ที่ตั้งไว้

วัด `gimbal.pivot_x_m`, `pivot_y_m` จากศูนย์กลาง chassis ถึงแกนหมุน Gimbal
และ `beam_offset_m` จากแกนหมุนถึงหน้าตัววัดตามแนวลำแสง ค่าเริ่มต้นเป็นศูนย์
ต้องตั้งให้ตรงตำแหน่งติดตั้งจริงก่อนใช้ระยะทำ mapping และตรวจว่า ToF มองได้
ครบสี่ทิศโดยไม่ถูกตัวหุ่นบัง รวมถึงปรับ `front_target_mm` ให้เข้ากับระยะเซนเซอร์
ถึงขอบตัวหุ่นและระยะกลางช่องจริง

ตรวจเครื่องหมาย yaw และแกน position ด้วยการทดสอบเลี้ยว/เดินหนึ่งช่องก่อนสำรวจ
คำสั่งเลี้ยว `chassis.move` ใช้ `robot.yaw_command_sign: -1` ส่วนคำสั่งรักษาทิศ
`drive_speed` ใช้ `robot.yaw_speed_command_sign: 1` แยกกันตามผล Log run6 ตัวเชื่อมตั้ง
SDK คง CHASSIS_LEAD ตาม repo อ้างอิงตลอดการสแกน และบันทึกมุม Gimbal ที่รายงาน
สัมพันธ์กับ chassis ([SDK source](https://github.com/dji-sdk/RoboMaster-SDK/blob/master/src/robomaster/gimbal.py))

ค่าเริ่มต้น `gimbal.scan_mode: gimbal` สแกนด้วย ToF บน Gimbal ขณะ chassis หยุด
ก่อนสแกนครั้งแรกใช้ `recenter()` เพียงครั้งเดียว ตั้ง reference เป็น 0° แล้วใช้ลำดับหน้า 0° → ซ้าย −90° → หลัง −180°
→ กลับกลาง 0° → ขวา +90° → กลับหน้า 0° หมุนครั้งละไม่เกิน 90°
ปรับจาก [repo อ้างอิง](https://github.com/nathon-aie/SLAM/blob/89b52817e970af4111e4519cd8956dcf8d443484/src/robot_controller.py)
โดยรอ action จบและรับข้อมูล ToF ใหม่ก่อนบันทึกแผนที่ เวลาพักเริ่มที่ 0.35 วินาที
โหมด `chassis` ยังเลือกได้ใน settings หากต้องการหมุนตัวหุ่นอยู่กลางช่องแทน
ระบบชดเชยตำแหน่งติดตั้ง ToF ตามทิศ chassis ของแต่ละระยะที่สแกน

การสแกน Gimbal ใช้ `move()` แบบสัมพัทธ์ตามมุมที่สั่งไว้ครั้งก่อน
แบ่งการเดินทางตาม `gimbal.move_step_deg` (90°) และรอ `settle_sec` หลัง action
ไม่มี recenter ซ้ำระหว่างช่อง และไม่มีการส่งคำสั่งหมุนแก้มุมจาก feedback
หลัง action จบและรอ settle จะรับ ToF สดที่ผ่านเกณฑ์ระยะ โดยไม่ตรวจมุม Gimbal
มุมจริงยังบันทึกใน telemetry สำหรับวิเคราะห์ แต่ไม่ใช้เป็นเงื่อนไขรับ ToF
Log JSON/CSV มี event `gimbal` พร้อมมุมเป้าหมาย มุมจริง และคำสั่ง move แต่ละครั้ง
Telemetry บันทึกมุมทั้งแบบสัมพันธ์กับ chassis และ ground จาก SDK เพื่อวิเคราะห์
กรณีติดขีดจำกัดทางกลหรือมุมอ้างอิงต่างกัน

## ความเข้ากันได้กับ SDK ตอนเชื่อมต่อ

`src/sdk_connection.py` แปลงค่า `conn_type` จาก YAML/CLI เป็น constant object
ของ SDK ก่อนเรียก `Robot.initialize()` เพราะ SDK รุ่นที่ติดตั้งเปรียบเทียบ string
ด้วย `is` ซึ่งทำให้ข้อความ `ap` ที่เท่ากันแต่เป็นคนละ object เกิด
`UnboundLocalError: proxy_addr` ได้ การแก้นี้อยู่ในโปรเจกต์ ไม่แก้ไฟล์ใน `.venv`
ใช้ทั้ง Calibration และ RobotSystem และรายงานข้อผิดพลาดเครือข่ายโดยไม่แสดง
traceback ในเมนู Calibration

### RoboMaster SDK: คำสั่งความเร็ว chassis ไม่มี ACK

SDK ชุดที่ใช้ส่ง `ProtoChassisSpeedMode` เป็น PUSH (`need_ack=0`)
แต่ `drive_speed()` เรียกตัวส่งแบบ synchronous จึงคืน `False` เมื่อไม่มี response
แม้ส่ง packet แล้ว ตัวโปรเจกต์ยกเว้นการตีความ `False` ว่าเป็นการปฏิเสธ
เฉพาะ method นี้ของ SDK และ protocol แบบ PUSH เท่านั้น โดยไม่แก้ไฟล์ใน `.venv`
คำสั่งจาก driver อื่นที่คืน `False` และ exception ยังถือเป็นข้อผิดพลาด
การเดินสำเร็จต้องยืนยันด้วย odometry จริง เซนเซอร์สด และ ToF ตรวจด้านหน้า
หากหุ่นไม่เดินจริงจะหยุดเมื่อหมดเวลา ไม่ถือว่าถึงช่องถัดไป

### ตรวจทิศและตำแหน่งเมื่อเดินหนึ่งช่อง

`navigation.max_heading_error_deg` (15°) และ `max_lateral_deviation_m` (0.15 m)
กำหนดขีดจำกัดระหว่างเดิน หากเกินจะหยุดและรายงาน `heading_deviation` หรือ
`lateral_deviation` ไม่ถือว่าช่องถัดไปถูกสำรวจแล้ว การเดินสำเร็จต้องผ่านระยะหน้า
ตาม `slam.cell_arrival_tolerance_m` เมื่อหยุดจากระยะเดินครบ
หาก ToF หยุดที่กำแพงหลังเดินอย่างน้อยครึ่งช่อง จะยอมรับว่าถึงช่อง
ตาม `navigation.front_wall_arrival_min_fraction` (0.5) โดยไม่บังคับครบ 60 ซม.
ตรวจซ้ำหลัง Sharp Centering ส่วนการหยุดฉุกเฉินหรือกำแพงตั้งแต่ต้นไม่ถือว่าถึงช่อง
ไม่มีเกณฑ์มุมหรือระยะด้านข้างเพิ่มเติมตอนถึงช่อง
Sharp ยังคงใช้ `navigation.nominal_side_mm` ซึ่งต้องวัดจากตำแหน่งติดตั้งจริง
ค่าเริ่มต้น 140 mm ไม่ได้เปลี่ยนตามข้อมูล run6 เพราะยังไม่มีระยะกลางช่องจริงยืนยัน

### ขอบเขตแผนที่และทางออก

`map.rows` และ `map.columns` กำหนดพื้นที่ที่หุ่นอนุญาตให้เดิน ไม่ได้กำหนดว่าขอบ
ต้องมีกำแพงจริง หาก ToF เห็นทางเปิดออกนอกขอบ จะบันทึก `wall: false` ตามที่วัด
พร้อม `boundary_blocked: true` ใน JSON และ event `boundary_open` ใน Log
DFS เลือกเฉพาะช่องภายในขอบเขต และตรวจปลายทางอีกครั้งก่อนส่งคำสั่งเคลื่อนที่
ทางออกนอกแผนที่จึงไม่ทำให้ภารกิจล้มเหลวและไม่ถูกใช้เป็นกำแพงสมมติสำหรับ localization

### สแกนโดยไม่สั่งหมุน chassis

โหมดสแกน Gimbal คง `CHASSIS_LEAD` ไม่สลับเป็น FREE และไม่เรียกวงควบคุม
ScanHeadingHold หรือปรับทิศ chassis ก่อน/หลังสแกน คำสั่งหมุนระหว่างสแกนส่งให้
Gimbal เท่านั้น ส่วนการเลี้ยว/จัดแนว chassis อยู่ในขั้นเตรียมเดิน
`scan_guard.max_heading_drift_deg` (3°) และ `max_position_drift_m` (0.03 m)
ใช้เฝ้าตรวจ telemetry โดยไม่สั่งหมุนแก้ มุมตัวหุ่นไหลเกินจะยุติสแกน
ส่วน position เปลี่ยนเกินเกณฑ์จะบันทึก `scan_position_drift` ครั้งเดียวต่อรอบสแกน
แล้วสแกนต่อ ไม่ยุติงานจาก odometry เปลี่ยนหลังหยุดล้อ
ToF และการอัปเดต mapping ไม่ใช้มุม chassis ตรงแกนกริดเป็นเงื่อนไขรับข้อมูล
การจัดทิศก่อนเดินยังทำงานแยกจากการสแกน
การหยุดนี้ไม่ใช่การล็อกทางกล ต้องยืนยันการไม่หมุนกับหุ่นจริง
ตั้งขนาดสนามผ่าน `map.rows` และ `map.columns` ให้ตรงสนามจริง เช่น 7×7

หลัง recenter ครั้งแรก การสแกน Gimbal ใช้เฉพาะ `move()` ไม่มีการส่ง
`chassis.drive_speed(0,0,0)` ซ้ำระหว่างมุมหรือ `gimbal.drive_speed(0,0)` หลัง action
เพื่อคงวิธีควบคุมด้วย position action ตาม repo อ้างอิง ก่อนสแกนยกเลิกและรอ
SDK auto-stop timer ที่เหลือจากการเดิน เพื่อไม่ให้ timer ส่ง speed packet ระหว่างสแกน
คำสั่งหยุดมอเตอร์ยังใช้เมื่อเกิดข้อผิดพลาด/ยกเลิก และตอนจบระบบ
ผลว่าการตัด speed packet เหล่านี้แก้อาการหมุนจริงได้หรือไม่ต้องยืนยันกับหุ่น

เพดานกรองซอฟต์แวร์ `sensors.tof_filter.max_valid` ปัจจุบันเป็น 5000 mm
เพื่อไม่ตัดตัวอย่าง 4199–4261 mm ที่บันทึกจากด้านหลังใน run22
ค่านี้เป็นเกณฑ์กรองของโปรเจกต์ ไม่ใช่การยืนยันระยะ/ความแม่นยำของฮาร์ดแวร์
Log มี event `tof_sample` ต่อทิศ และ `tof_sample_failed` พร้อมจำนวน packet สด,
จำนวนตัวอย่างที่ผ่าน เกณฑ์กรอง และค่าที่ถูกปฏิเสธ เพื่อแยกข้อมูลหายจากการถูกกรอง

หลังเดินแต่ละช่อง ใช้ reference Gimbal เดิมและสั่ง move กลับหน้า
โดยไม่หมุนแก้จากมุมจริง Log `hardware_action` ระบุชื่อ state และเวลาของ
คำสั่ง move เพื่อวิเคราะห์ action ที่ล้มเหลวหรือหมดเวลา

หลังเดินครบช่อง ใช้ `drive_wheels(0,0,0,0)` เพื่อหยุดล้อด้วย request ที่มี ACK
แทนการอาศัยเพียง `drive_speed(0,0,0)` แบบ PUSH ก่อนเริ่มสแกนช่องถัดไป
ยกเลิก timer เก่า พักตาม `slam.stationary_settle_sec` แล้วรับ pose สด
ไม่มีการเริ่มจับเวลานิ่งใหม่จากความคลาดเล็กน้อย หากไม่มี ACK หรือ pose สดจะยุติ
Log ระบุ `chassis_wheel_stop` และ `chassis_stationary` เพื่อยืนยันการส่งต่อแต่ละช่อง
คำสั่งหยุดล้อนี้อยู่หลังการเดิน ไม่ส่งซ้ำแทรกระหว่าง Gimbal หมุน

ก่อนสแกนครั้งแรก พักตาม `slam.startup_settle_sec` (1 วินาที) แล้วรับ pose สด
แล้วจึงจับ baseline ของ scan guard เพื่อไม่ใช้ตำแหน่งแรกที่ SDK ยัง reset counter
เหมือน run25 ซึ่ง raw position กระโดดจากค่าค้างไปใกล้ศูนย์ขณะความเร็วเป็นศูนย์
ขั้นรอนี้อ่านเซนเซอร์อย่างเดียว ไม่ส่งคำสั่ง chassis หรือ Gimbal และไม่เพิ่ม tolerance

ระยะ ToF ที่สั้นกว่าระยะกำแพงตามเรขาคณิตช่องจะบันทึกด้านนั้นเป็นกำแพง
โดยไม่ยุติการสำรวจด้วย `Unexpected obstacle inside the cell` เพื่อให้ DFS
เลือกทางเปิดอื่นต่อได้ การตรวจ ToF เพื่อหยุดก่อนชนระหว่างเดินยังทำงานตามเดิม

ข้อมูลสแกนที่ไม่ตรงกำแพงเดิมจะบันทึก `range_mismatch` หรือ `wall_mismatch`
และสำรวจต่อ โดยข้ามการแก้ตำแหน่งจากระยะที่ขัดกันและรักษา edge เดิม
ToF กันชนระหว่างเดิน, Sharp Centering และขอบเขตแผนที่ยังทำงาน

`gimbal.hold_front_on_move: true` สั่ง `moveto(yaw=0, pitch=0)` ครั้งเดียวก่อนเริ่ม
เลี้ยวหรือเดิน แล้วใช้ CHASSIS_LEAD เดิมโดยไม่ส่งคำสั่ง Gimbal ระหว่างเดิน
รับ ToF สดหลังกลับหน้าก่อนเปิดการเคลื่อนที่ Sharp Centering และกันชนยังทำงาน
เป็นการใช้ position control ของ SDK ไม่ใช่ล็อกทางกล ต้องทดสอบการรักษามุมกับหุ่นจริง

ขณะหยุดสแกน หาก pose เก่าเกิน `slam.max_sensor_age_sec` (0.3 s) จะพักรอ
ข้อมูลสดได้อีก `slam.scan_pose_recovery_timeout_sec` (2 s) โดยไม่ส่งคำสั่งมอเตอร์
ข้อมูลกลับมาจะสแกนต่อและตรวจการเคลื่อนจริงเทียบกับ baseline เดิม
เวลารอ pose ไม่กินเวลาสำหรับเก็บ ToF ใหม่; ถ้าขาดต่อเนื่องจนหมดเวลาจึงยุติ
Log มี `scan_pose_wait` และ `scan_pose_recovered` การตรวจข้อมูลสดขณะเดินคงเดิม

หลังเดินครบช่อง ความคลาดตำแหน่งจากกลางช่องเกิน `slam.localization_gate_m`
จะบันทึก `odometry_mismatch` แล้วสำรวจต่อ ไม่ยุติงานจากความคลาดสะสม
ค่านี้ยังใช้กรองระยะที่ไม่ตรงกำแพงเดิมก่อนแก้ตำแหน่ง การตรวจระยะเดิน
ToF กันชน ข้อมูลเซนเซอร์สด และการห้ามออกนอกแผนที่ยังคงเดิม

เมื่อสำรวจจบ (สำเร็จ/ยกเลิก/ผิดพลาด) จะเก็บไฟล์แยกใน `telemetry_logs/runN/`:
- `map.png`: แผนที่และเส้นทาง พร้อมหมายเลข step
- `actions.html`: รายการ step/action เปิดด้วย browser ได้โดยไม่ใช้อินเทอร์เน็ต
  ค้นหาได้ พับ/เปิดรายละเอียดแต่ละ step ได้ และมีปุ่มเปิดทั้งหมด
- `events.csv`: event ทั้งหมดสำหรับวิเคราะห์เพิ่มเติม
- `runN_TIMESTAMP_map.json`: สำเนาแผนที่ของรอบนั้น

Step 0 คือสแกนจุดเริ่ม หมายเลขบน map ตรงกับ step เดิน/ย้อนกลับในรายการ
พิกัด (x,y) คือช่องในกริด คำสั่งเลี้ยวที่อนุมานจาก log เก่าระบุ planned/inferred
